## 一、链路总览（现状）

```
用户故事（整理后中文）
 │
 ├─【雅思流】首页泛题池选题(带 qid) → 写故事 → 整理 → 直达题目分析（跳过匹配）
 │
 └─【故事流】写故事 → 整理 → 进入匹配
      │
      ▼
   [1 萃取] 主观察点 + 副观察点          extraction.ts
      │
      ▼
   [2 三层漏斗召回 + 邻居增援]           matching.ts
      │  L1 主观察点（含副挂题）
      │  L2 主空 → 故事副观察点          matchedViaSecondary
      │  L3 召回<3 → 邻居增援            matchedViaNeighbor
      │  三层全空 → noMatch（实测 0/100）
      ▼
   [3 重排打分 0-100]                    ranking.ts
      │
      ▼
   [4 分档展示]                          matching/page.tsx
      │  高≥85(首屏)/中60-84(折叠)/低40-59(折叠)/<40隐藏
      │  全局无可见题 → NoMatchView 引导
      ▼ 用户选题
   [5 题目分析]（不依赖观察点）          analysis.ts
```

**分流关键**（`restructure/page.tsx:119-124`）：带 `qid` → `/analysis`（雅思流，跳过匹配）；无 `qid` → `/matching`（故事流）。因此 `topic_only` 题目**不需要观察点映射**，它们只经首页泛题池进入，不走召回。

## 二、逐步详解（现状）

### 1. 萃取（extraction.ts）
输入整理后的故事，输出主观察点（必有）+ 副观察点（极少给）。

- **观察点体系：当前 48 个**（DB `observation_points` 表为准）
- 副观察点严格定义：两段当下并存、各自撑得起一道口语题的独立叙事层
- Prompt 含决胜总则 A~D（模式vs单次／内核vs载体／重心迁移／摩擦vs正义）
- 质量基线：严格命中 94.9%／宽容 97.6%（金标 v2，100 条；人类双标一致率 99%）
- 回归：`npm run eval:extraction -- --runs=3`

### 2. 三层漏斗 + 邻居增援（matching.ts · matchByStory）
- **L1 主观察点**：`collectFrom(primary, true, includeSec=true)`，主挂 + 副挂题都召回
- **L2 故事副观察点**：仅当 L1 为空时借道 → `matchedViaSecondary=true`
- **L3 邻居增援**：召回总数 < `NEIGHBOR_MIN`(3) 即触发（不论 L1/L2 是否命中），按 `observation-adjacency.ts` 借主观察点的语义邻居补题，累计 ≥`NEIGHBOR_TARGET`(5) 或邻居用尽即停 → `matchedViaNeighbor=true`，`neighborPointsUsed` 记录所借邻居。去重全程生效，不增加 LLM 调用
- **noMatch**：仅三层全空。remap + 邻接后实测 0/100

### 3. 重排（ranking.ts）
对全部召回题逐题打 0-100 分。判定主线：「要不要改动故事本身」。
- 喂给 AI 的候选结构：`{id, en, zh, obs}`，其中 `obs` = **DB 的观察点 name**（注意：这意味着 DB 的 name 直接影响打分，不只是显示用）
- 题面由 `questionFace(q)` 统一构造（见第五节）
- 降级：重排失败返回空分时，前端将无分题目视为高匹配全量展示（保可用性）

### 4. 分档展示（matching/page.tsx + Desktop/Mobile）
| 分数 | 档位 | 呈现 |
|---|---|---|
| ≥85 | 高匹配 | 首屏直接展示 |
| 60-84 | 中匹配（换角度/补充信息能答） | 折叠"查看更多" |
| 40-59 | 低匹配 | 折叠"查看更多" |
| <40 | 隐藏 | 不展示、不入库 |

**两类"空"**：
- `noMatch`（三层全空）→ NoMatchView（variant='noMatch'）
- `globalNoneVisible`（有题但全 <40，跨 Tab 无可见题）→ NoMatchView（variant='lowScore'）
- Tab 局部空（当前 Part 无题、其他 Tab 有）→ 轻量灰字，不误升级

### 5. 题目分析（analysis.ts）
输入 = 题目(part/en/zh) + 可选故事，**不使用观察点**。
- `enForAI = q.question_text`（完整 cue card）｜`enForDisplay = cue_card_title`（短标题）
- 这个"喂AI用完整、展示用标题"的模式是正确基准；practice.ts 同样遵守

### 6. Part3
不参与匹配（0 观察点映射），在练习对话中经 Part2 引入。

## 三、关键口径（易混，务必分清）

| 术语 | 含义 |
|---|---|
| noMatch | 三层召回均为 0（实测 0/100） |
| globalNoneVisible | 召回到题但全部 <40 被隐藏，跨 Tab 无可见题 → NoMatchView |
| noneVisible（Tab 局部） | 仅当前 Part Tab 无可见题 → 轻量灰字 |
| matchedViaSecondary | L2 借故事副观察点召回 |
| matchedViaNeighbor | L3 借邻接表邻居补题（召回<3 触发） |
| 中匹配 | 重排 60-84 分。与邻居增援是两件事：前者是打分档位，后者是召回来源 |
| topic_only | 题目属首页泛题池，经 qid 直达分析、**不走召回**；与链接表独立 |

## 五、题面构造：questionFace（单一事实源）

`src/lib/question-face.ts` 的 `questionFace(q)` 是题面的唯一构造入口，保证「AI 看到的题面」与「盲标表给标注人的题面」完全一致。

```
Part2（cue_card_title 非空）→ `${cue_card_title} — ${question_text}`（标题 + 完整题面含 You should say bullet）
Part1/3                     → question_text
```

**历史教训**：此前 `matching.ts` 写作 `cue_card_title ?? question_text`，Part2 短路成裸标题，完整题面被丢弃 → AI 在信息残缺下打分。表现为「首屏精确率 22%／虚高率 54%」，实为管道 bug 的度量，非 AI 判断力的度量。**任何新增题面消费方，必须走 questionFace，不得自行拼接。**

**当前采用方**：`matching.ts`、`scripts/eval/run-ranking.ts`
**尚未采用**：前端 9 处 Part2 展示仍用 `?? cue_card_title` 裸标题（产品已决策要展示完整题面，排期中）

## 六、观察点邻接机制

`src/lib/observation-adjacency.ts`，每点配 3 个邻居，按优先级排序。
- 设计原则：优先同维度、语义近、邻居有题
- 题库结构性缺口的点（EMO_11 失眠、REL_05 亲密关系），首邻居均为有题大户（EMO_02、REL_03），确保恒有可达题源
- 邻居题进重排后多落中/低档 —— 与「换角度能答=中匹配」语义自洽

### 7.1 新增观察点 REL_12「一个让你印象深刻的人」（48 → 49）
填补 REL_03（密友）与 REL_06（陌生人）之间的「熟人层」：同事/邻居/长辈/老师/店主/同学等"认识但非密友"的人物描述。

- ⚠️ **REL_06 vs REL_12 硬边界（易咬人，2026-07-16 S036 案例，已改 prompt 并回归验证通过：S036 3/3 归 REL_06、全集 REL_12 误判归零）**：唯一硬线 = **这个人你能不能反复见到**。不能（一面之缘/偶遇），无论多聚焦其人本身，都是 REL_06——哪怕简短交谈、听其自述（交谈≠认识，"无信息交换"不是 REL_06 的条件）；能反复见到的熟人（同事/邻居/长辈/老师/店主/同学）才归 REL_12。**为什么必须堵**：REL_12 的 7 张卡真题全问 "how you knew him/her"，陌生人故事一张都答不了——误吸 = 把故事送进它根本答不了的题（注：REL_06 零挂题、S036 走邻居兜底照样拿到那 7 张卡，故这条主要是**金标完整性**问题、非体验问题）。**修法教训**：首版把边界句放进 REL_12 定义没用——模型自造"REL_06=无信息交换"的过窄误读绕过去；把硬线**正面写进 REL_06 自己的定义**、并用"能否反复见到"这个**客观判据**，才 3/3 纠正

## 九、流程铁律

1. 改 prompt / 换模型 / 改映射 → 先跑对应 eval → 报告进 git → 再合并
2. **指标大面积异常时，先跑 `@pipeline-auditor` 审管道，再讨论 AI 判断力。** 本项目已三次吃亏于此：题库映射没做全（31% noMatch）、题面喂半截（22% 虚高）、映射基于残缺标题（24/63 错）——三次根因都是"喂给 AI 的东西不对"，但第一反应都是去调 prompt
3. 任何题面消费方走 `questionFace()`，不得自行拼接
4. 造考卷（金标）只能由人 + 主会话完成，任何 subagent 无权写 `scripts/eval/golden/`
5. **噪声阈值 ≠ 无视已知结构错误的许可证**：萃取回归 run-to-run 噪声阈值约 **±1.5pp**（稳定性 ~98%）。整体波动低于阈值只说明"这次不算真回归"，**不等于**可以放过阈值内的**已知结构性错误**。判据：**同一条 3/3 运行一致命中同一错误 = 结构错误，必修**；单次偶发 = 抖动，先记账观察、下轮复看。噪声阈值是防"把抖动当改进"，不是"低于阈值就无视已知错误"的护身符。前车之鉴：2026-07-16 S036（单次陌生人被 REL_12 吸走），整体 −1.3pp 在噪声内、技术上闸门通过，但 3/3 一致，是真结构错误，标记必修。⚠️ 更深的坑：首次 prompt 补句后重跑，整体严格命中"恢复"到 94.9%（基线值），但这是**巧合**——S036 仍 3/3 判 REL_12 纹丝未动，只是另一条抖动条目（S041）恰好恢复、又冒出一条新抖动（S100）把总分填平了。**看总分会以为修好了，看条目才知道没修。**这正是本铁律要防的：别用聚合数字确认单条结构错误是否修复，必须逐条核对目标条目本身。收尾：同日 A′ 硬边界版 prompt（把规则正面写进 REL_06 定义 + "能否反复见到"客观判据）重跑，S036 3/3 归正、REL_12 误判归零，**确认修复——依据仍是逐条核对，不是总分**
