## 一、要解决的问题（已用生产埋点与真机截图确证，不必重新诊断）

`globalNoneVisible` 的定义门控了 `streamDone`：

```ts
const globalNoneVisible = !!result && streamDone && !result.noMatch && totalVisible === 0
```

产品方实测那个语料匹配跑了约 50 秒，于是流式期间 `streamDone=false`，页面落进 `isNormal` 分支：

- 桌面端：大标题「匹配到 **0** 道当季真题」+ **完全空白的左栏** + 右栏「从左侧选择一道题查看详情」。左栏只渲染 `highGroup`/`midGroup`，而这次 5 道题全部低于 `SCORE_MID`，**全被两个分档过滤掉**。连「该 Part 暂无匹配题目」都不出现，因为 `noneVisible` 也门控了 `streamDone`。
- 约 50 秒后 `streamDone` 置真，**整页跳变**成 `LowMatchView`。

「退回再进来不一样」的真相：第一次 `served_from: fresh`（真跑，完整经历那 50 秒），退回再进 `served_from: cache`（约 0.2 到 0.6 秒，那个错误画面被压缩成一次闪烁）。**验收时不要用 cache 路径，会看不出问题。**

## 二、统一状态机（两端唯一真源）

新建 `src/app/matching/phase.ts`，纯函数 + 单测，**不碰任何阈值、不改 `lowShown` 派生、不回填占位分**：

```ts
export type MatchPhase =
  | 'waiting'    // 还没有任何可展示的题（首次加载 / 流式中途 totalVisible=0）
  | 'streaming'  // 流式未完成，但已有可展示的题
  | 'result'     // 定稿，有可展示题
  | 'lowMatch'   // 定稿，无可展示题，但 lowShown 非空
  | 'noMatch'    // 定稿，一道题都没召回
  | 'degraded'   // 定稿，重排没产出（含 globalNoneVisible 且 lowShown 为空）
  | 'error'      // 请求失败
  | 'limit'      // 当日上限 429
```

判定顺序即优先级：

```
limit → error → (!streamDone ? (totalVisible > 0 ? 'streaming' : 'waiting'))
      → noMatch → degraded → lowMatch → result
```

**关键**：`waiting` 的门是 `!streamDone`，不是 `loading`。`loading` 在第一个 question 帧就变 false，而低相关场景 `totalVisible` 恒为 0，这正是「匹配到 0 道 + 空白左栏」持续 50 秒的成因。

`page.tsx` 新下发的 props（全是呈现层状态）：

| prop | 来源 |
|---|---|
| `phase: MatchPhase` | 上面的纯函数 |
| `streamDone: boolean` | 已有 state，只是没下发 |
| `candidateCount: number \| null` | `onMeta` 帧的 `meta.candidateCount`（当前被丢弃，要存下来） |
| `arrivedCount: number` | `result.questions.length` |

`?stream=0` 降级路没有 meta 帧，`candidateCount` 为 null，计数行**整行不渲染**（不显示假分母）。

## 三、桌面统一骨架

结构与现有 `result` 态逐字一致，其他所有状态改成填这个结构。四个槽全程存在，**从进页面到结果到齐一次都不重建**。

```
<div className="h-[calc(100vh-72px)] flex flex-col items-center px-8 py-8 overflow-hidden">
  <div className="w-full max-w-[1040px] flex-1 min-h-0 flex flex-col">

    ① 头部（shrink-0 mb-5）
       h2   text-[1.375rem] font-bold text-v2-text-primary   ← 状态化标题
       副行 text-[0.8125rem] text-v2-text-muted mt-1          ← 识别维度（恒占一行）

    ② 状态说明卡（shrink-0 mb-5）
       <Card className="px-4 py-3 min-h-[76px]">             ← 恒在，内容状态化
       role="status" aria-live="polite"

    ③ 两栏（flex-1 min-h-0 flex gap-6）
       左 w-[360px] shrink-0 flex flex-col min-h-0
          · Part 筛选槽（h-[2rem] 恒占位；须用 rem——Chip 字号随字体档缩放，px 定高在大字档必裁）
          · 列表区（flex-1 overflow-y-auto）← 骨架卡 / 真卡分组 / 无题说明行
       右 flex-1 min-h-0 flex flex-col justify-center
          · 面板 ← 等待说明 / DetailPane / 出口面板

    ④ 键盘提示行（shrink-0 mt-4 text-center text-[0.75rem] text-v2-text-muted）
  </div>
</div>
```

**右栏为什么保留、低相关态也保留**：原注释担心 `TierBadge` 给低于 60 分的题算出「中匹配」自打脸。那不是版式问题，是徽标只有两档的问题。第五节给 `tierOf` 补第三档后右栏不再自打脸，两栏骨架得以保住。

## 五、八种状态的呈现与文案定稿

### 通用副行（识别维度）

- 有 `primary`：`识别维度：{dimension} · {pointName}`（有 secondary 时追加 ` ／ {dimension} · {pointName}`，与现状一致）
- 无 `primary`：`识别维度：识别中`；error / limit 态渲染同高度空占位 `<p aria-hidden="true">`，不放假信息

meta 帧在萃取完成时就到（早于全部重排），所以等待期中后段这行会自己填上真值，是一次正向的「有进展」信号。

### 状态 1：waiting

| 槽 | 内容 |
|---|---|
| 标题 | `正在为你匹配题目` |
| 说明卡 | `<MatchingProgress>`（阶段文案 + 进度条）+ 已评估计数行 |
| Part 槽 | 骨架 chip ×2（桌面）/ ×3（移动），`aria-hidden` |
| 列表区 | 骨架卡 ×4（桌面）/ ×3（移动），沿用现有骨架样式，`aria-hidden` |
| 桌面右栏 | 说明面板：`题目还在陆续到达，到了会显示在左边` + 小字 `选中任意一道，这里会展开它和你的语料的关系` |
| 移动底部槽 | 空占位 |

**🔴 不写时长承诺。** UX 原稿建议「整段匹配通常 1 分钟内完成」，**已否决**。核过的真实数据：服务端单次调用近 14 天 247 次，p50=5.5s、p95=30.6s、最慢 56.4s；用户端到端是 extraction + ranking 串联（平均约 19s），而客户端埋点里**有一次 134 秒**。任何具体数字都会被这类样本当场证伪，而承诺被证伪比不承诺更伤。预期管理改由进度条 + 真实计数承担。

- 已评估计数行（`arrivedCount >= 1 && candidateCount` 时才出）：`已评估 {arrivedCount} / {candidateCount} 道候选`
- 超时兜底（`elapsed > 75s && !streamDone`，追加一行 + 文本按钮）：`比平时久了一些，还在算。可以再等等，也可以重新匹配一次。` 按钮 `重新匹配` → `onRetry`
- `src/lib/matching-progress.ts` 的 `STAGES` 追加一档（现在最后一档停在 10 秒，50 秒的语料会盯着同一句话看 40 秒）：`{ fromMs: 30_000, text: '还在逐题评估，这次候选题有点多…' }`
- `progressPct` **不动**（已是 20 秒到 85% 后渐近逼近 99% 永不到顶，是诚实的）。计数行与进度条并行，**不拿计数驱动进度条**，避免进度条倒退。

### 状态 2：streaming

| 槽 | 内容 |
|---|---|
| 标题 | `已找到 {totalVisible} 道，还在继续找` |
| 说明卡 | 与 waiting **完全相同**（同一个 `MatchingProgress` 实例，见第七节陷阱一） |
| Part 槽 | 真 chips |
| 列表区 | 真卡片分组（高/中） |
| 桌面右栏 | `DetailPane` |
| 移动底部槽 | 空占位（折叠开关等定稿后再出，避免数字跳动时开关反复出现） |

waiting → streaming 只是骨架卡换成真卡、标题数字变化，**没有任何结构变化**。

### 状态 3：result（按有没有高匹配分两种情况）

| 槽 | 有高匹配（情况一） | 只有中匹配（情况二） |
|---|---|---|
| 标题 | `匹配到 {totalVisible} 道当季真题`（不变） | `暂无完美匹配` |
| 说明卡 | 第一行 `下面这些题，都可以用你刚才那段语料来回答`；第二行 `先挑一道进去，分析会告诉你这段语料该怎么组织成答案。` | 一行 `换个角度，可以匹配到下面这些题目。` |
| 列表 | 高匹配展示、中匹配折叠 | 中匹配自动展开（既有 autoExpand 行为） |
| 其余 | 与现状一致；移动底部槽放 `查看更多 {foldedCount} 道 →` / `收起 ↑`，无折叠内容时空占位 | 同左 |

情况二仍是 `phase='result'`，按「跨所有 Part 有没有 ≥SCORE_HIGH」（结果级属性，不随 Tab 变）切标题与说明卡。

`matchedViaSecondary` 为 true 时说明卡换成现有那两行副维度说明，**一字不改**（已验证过，且这张卡从此有固定位置，不再是「有时冒出一张卡」）。

### 状态 4：lowMatch（产品方这次的核心诉求，文案为 2026-08-03 定稿）

| 槽 | 内容 |
|---|---|
| 标题 | `暂无可用匹配` |

## 六、保住右栏的代价：四处不能自打脸的地方

**1. `TierBadge` 只有两档。** `tierOf` 补第三档（只读既有 `relevanceScore`，**不碰 `SCORE_MID` / `SCORE_HIGH`**）：

```ts
type Tier = 'high' | 'mid' | 'low'
// score >= SCORE_HIGH → high；>= SCORE_MID → mid；否则 low
```

`low` 档文案 `不够贴合`，样式 `text-v2-text-muted bg-black/[0.04] border-black/[0.08]`（对近白 5.09:1，达 AA，不新增 token）。

⚠️ `tierOf(undefined)` 现在会打 `console.error` 后**照样返回 `'mid'`**。降级态（分数全缺）下这等于「知道自己不知道，还是说了」，必须一并处理：无分数时不渲染徽标。

**2. `DetailPane` 的「为什么这道题适合你」在低相关态是谎话。** 标题按档切：`tier === 'low'` 时改为 `这道题和你的语料差在哪`，正文仍用同一个 `relevanceReason`（重排对低分题照样给 reason，不需要新数据）。

**3. 「需切换角度」标签在「全都不贴合」语境下有害。** 条件是 `!isPrimaryMatch && !isHighMatch`，低相关态只有一部分卡会挂上，等于暗示「没挂标签的那几道不用切换角度」，而实际一道都不能直接用。给 `MatchedQuestionCard` 和桌面 `QuestionRow` 加 `showSwitchTag?: boolean`（默认 true），低相关态传 false。

**4. 键盘与自动选中的数据源要跟着换。** 现在 `ordered = [...highGroup, ...midGroup]`、筛选联动用 `filtered`，低相关态两者都是空，会导致 ↑↓ 无效、右栏空白：

```ts
const listItems = phase === 'lowMatch' ? lowShown : [...highGroup, ...midGroup]
```

`ordered`、自动选中 effect、`hasList` 全部改读 `listItems`。**漏了这步低相关态桌面键盘就走不通。**

## 七、三个实现陷阱（踩中会直接毁掉方案）

**陷阱一：`MatchingProgress` 重挂载会让进度条倒退回 0。** 它的计时器以挂载时刻为起点。若 waiting → streaming 换了 JSX 位置，React 会卸载重建，进度条从 85% 掉回 0，用户会认为「又从头开始了」。**要求：`<MatchingProgress>` 在 waiting 与 streaming 两个 phase 里必须处于同一 JSX 位置、同一父链、不带变化的 `key`。** 这正是把它放进「恒在的状态说明卡」而不是各自分支的原因。

**陷阱二：降级重发 `?stream=0` 期间。** 此时 `streamDone` 仍为 false、`result` 可能是残缺的流式中间态。按新状态机它自动落在 waiting/streaming，页面继续显示进度而不是「结果」，顺带修掉现在这条路径上「用户看着半截列表以为这就是全部」的隐患。计时器不重置是对的：用户等的是同一次匹配的总时长。

**陷阱三：`streamDone` 迟迟不来又不报错。** 现在没有任何逃生口。75 秒兜底行 + `重新匹配` 文本按钮就是那个出口。注意重试会真的再跑一次模型（多一次 AI 费用 + 多计一次当日配额），所以做成低强度文本按钮、放说明卡里而不是显眼 CTA。
