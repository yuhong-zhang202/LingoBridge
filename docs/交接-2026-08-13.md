## 五、本批次沉淀的教训（都已应验，写进 `CLAUDE.md` 验证纪律）

1. **验证提交内容要读 HEAD 树，不能读索引。** `61bc553` 声称撤销了误跟踪文件，实际只改了 `.gitignore` —— 因为 `git commit -- <路径>` 从**工作区**取内容提交、绕过了 `git rm --cached` 的暂存状态。当时用 `git ls-files`（索引）验证，看到的是假象；`git ls-tree HEAD` 才是真相。
2. **搜索否定性结论要换维度复核。** 曾断言「`supabase_data` 不存在」，实际目录名是 `临时supbase_data`（`supbase` 少个 `a`），按正确拼写 grep 必然扑空。改用**按文件类型扫**才把面扫全。
3. **agent 审代码前先确认分支。** 详见 memory `feedback-agent-branch-context`：红队在落后 317 个提交的工作区里 grep，报「全仓零命中」，据此否掉了一个**完全正确**的修复方案。
4. **台账编号会撞车。** 两条线各自从条目 122 之后续编，`main` 侧 123–131、分支侧 123–147，而条目之间按编号互相引用。合并前必须检查编号区间。
5. **数字先核实再报。** 本批次两次报错数：匿名号成本上界（¥3.3 → 实际 ¥45）、匹配往返次数（「串行 118 次」→ 实为 `Promise.all` 并行）。
