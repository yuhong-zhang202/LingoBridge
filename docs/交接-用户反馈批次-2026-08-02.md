## 四、安全 hotfix（已完成，记录备查）

两条都是**当时生产上已经成立**的问题，由 security-auditor 真实探测发现、协调者独立复核确认，非推理。

**① 8 个经营指标 RPC 对匿名全开放**
持浏览器里公开的 anon key、未登录即可直读留存率 / 注册总数（113）/ 逐日注册明细 / 激活率，绕过 `/api/dashboard` 的 `requireAdmin` 闸。根因：`0043-0048` 建函数时只写 `grant to service_role`、没有先 revoke，而 PG 对新建函数默认 `GRANT EXECUTE TO PUBLIC`，Supabase 的 default privileges 又额外给了 `anon=X`。

**② avatars 桶可被匿名枚举出全部用户 user_id**
`POST /storage/v1/object/list/avatars` 返回 UUID 目录名，而路径就是 `avatars/{userId}/{ts}.{ext}`、桶公开读，可据此批量下载人脸（PIPL 敏感个人信息）。修复砍掉的是「不知道 user_id 也能列出全部 user_id」这一环；已知完整路径的头像**仍可公开访问**（产品要的外链设计），但 uuid v4 不可枚举，链已断。**不要对外描述成「头像变私密了」**。

**给未来的人**：任何新增 security definer 函数 / 视图 / 存储策略，**必须自带 revoke**，正确范式见 `0041`。验 ACL 用 `has_function_privilege('anon'|'service_role', fn, 'execute')`，**不要在 SQL Editor 里直接调函数验证**，那里以 postgres 超级用户身份跑、绕过一切 ACL、必然成功。

## 五、真机怎么连（下次还要用）

- 局域网 IP + 明文 HTTP（`http://192.168.0.209:3001`）**测不了录音**：`navigator.mediaDevices` 在非安全上下文下是 `undefined`，浏览器直接把麦克风 API 藏起来。`localhost` 是唯一例外。
- `npm run dev:https` 在本机**跑不通**：`mkcert -install` 要输密码（非交互环境失败），且它生成的证书只覆盖 `localhost 127.0.0.1 ::1`、不含局域网 IP。
- **可用做法**：`cloudflared tunnel --url http://localhost:3001`（本机已装），拿到一个真证书的公网 HTTPS 地址，手机直接开、不用装任何东西。注意隧道走公网有额外延迟，**别用它判断快慢**。

### 3.5 `capture_abandoned` 的口径重定（本批查实的已知限制，需设计官定）

**现状：这一格实际只覆盖「关标签页」，比预期窄得多。** 代码里写的是「`pagehide` 事件 `persisted=true`（进 bfcache）就不报」，本意是「别把马上回来的人算成放弃」，但**桌面 Chrome 地址栏跳走、点链接离开，通常都进 bfcache**，于是这些最典型的放弃行为一律不记。

**取证过程值得记（一次诊断被推翻的案例）**：
1. qa-engineer 实测生产构建下 `pagehide` 出口 0/8，诊断为「`track()` 里 `await authHeaders()` 在卸载窗口跑不完、fetch 压根没被创建」，并有同窗口同步探针 13/13 的对照支持。
2. fix-engineer 按此实现同步 keepalive 路径后做 A/B 复测，**改前改后无差别**，继续取证发现：① QA 那 0/8 的直接原因是 `e.persisted=1`、**代码根本没走到 `track`**（QA 的探针把 persisted 值聚合掉了）；② 关掉 bfcache 后**修复前的代码照样创建出带鉴权头的 keepalive fetch**（10/10），await 不是丢失点；③ 加透明代理定位残余丢失：**8 个已创建的请求只有 2 个到达服务端，到达的 100% 落库**，丢在「浏览器已创建 → 真的发出去」这一段，与我方代码/鉴权/落库无关。
3. 同步 keepalive 的改动**保留但不宣称修好**（消掉卸载路径的异步依赖，代价为零、无回归），实测结论已写进 `client-events.ts` 顶注，避免后人看到「已改成同步」就以为这格准了。

**【2026-08-03 已定案，结论是「代码不用改」】** `metric-designer` 出方案后确认：

**`capture_abandoned` 的丢失概率与「用户怎么离开」强相关**（站内跳走 3/3 到、关页 0/8），越是「彻底不玩了」越报不出来。这是**方向已知、大小未知的系统性偏差，任何修法都消不掉**：修好 bfcache 也只是把「一律不报」换成「不可靠地报」，率照样不能用。

**定案**：
1. **放弃率整个搬到离线推断口径**：有 `capture_started`、但窗口内该 user 没有新增 `corpus` 行 = 放弃。它的输入丢失与结局无关（`capture_started` 在挂载时报、早于用户做任何决定；`corpus` 是服务端事实、系统外的量），**率无偏**，只是样本略小。
2. **`capture_abandoned` 事件降级为「归因样本」，永久禁止做任何比率的分子**（已把这段警告钉进 `src/lib/events.ts` 的类型定义处；注释挡不住表名的诱惑，但至少改的人会看见）。它保留的唯一实质价值是 `durationSec` / `charCount`：区分「进来 3 秒就跑」与「录了 90 秒才跑」，这两者的产品动作完全相反，而推断口径拿不到这个。
3. **不做 `pageshow` 撤销方案**：要新增事件名 + 改三处手抄定义 + 一套只能按 user_id 和时间邻近做的离线配对（`flow_id` 已知不可用），而且撤销事件一旦丢，偏差方向会从「可解释的偏低」翻成「不可分辨的偏高」，更坏。
4. **历史数据不作废、可直接拼接**：推断口径不消费 `capture_abandoned`，`capture_started` / `capture_submitted` / `corpus` 的语义一个字没变，2026-08-02 起的数据原样进新口径、无断点。

**净改动量**：代码零改动（除上述警告注释）。要新增的是**一段离线口径 SQL** + **一份判例集**（人标约 1 人日，60 条采集会话，用于定 `N`「产出观察窗」与 `GAP`「会话切分间隔」两个参数）。判例集格式对齐 `scripts/eval/golden/extraction.v2.json`，**绝不导出故事原文**。

### 5. ~~polish 的 500 字符上限~~ ✅ 已完成（2026-08-03，上限改 800）

**做法**：上限 500 → 800（覆盖率 92.5% → 98.6%），**并捆绑补上 `timeoutMs` 与 `maxTokens`**。
polish 此前是全项目唯一一个两者都没设的 `callLLMJson` 调用，吃 `llm.ts` 的 30s 默认。
不补的话，输入放宽 → 输出跟着长 → 撞超时或 token 上限 → 走 fallback → 用户**等 60 秒才看到「请重试」、
点了按钮再等 60 秒再失败**，等于把刚修掉的「假重试死循环」以更坏的形式复活。

**标定有实测支撑**：现网 47 条真实调用拟合出「1.5s 固定开销 + 19ms×completion_token」，
另补打 3 次真实长输入调用（737/814 字符 → 306/456/421 tokens → 6.4/12.9/8.0 秒），
定为 `BASE 11s + 12ms/字符`（800 字符处 21.6s，最紧一次仍有 1.7× 余量）、`maxTokens 1024`（2.2× 余量）。
**取舍方向与 analysis 相反且刻意**：analysis 无 fallback、超时=报错页所以「宁可给宽」；polish 有 fallback
且内部重试一轮，**用户感知的最坏等待 = 2×预算**，所以这里「宁可给紧」。加了测试守住 ≤25s 上界防后人改宽。

**⚠️ 待观察**：12ms/字符的斜率只有 3 次实证，最慢那次生成速率比 47 条拟合值慢近 5 成，**可能没摸到慢尾**。
**观测点**：盯 `api_usage_logs` 里 `phase=polish` 的 `latency_ms` 有没有开始出现贴近 20s 的值、
有没有 `status=error` 行（目前 0 条）。出现即回来上调 BASE 或 PER_CHAR，复标条件已写进代码注释。

**顺带修掉一个记账错误**：成本兜底估算里的常量 `400`（估 prompt tokens）**低估近 3.5 倍**，
实测 `POLISH_SYSTEM` 基线约 1400。这也印证了「输入上限=防刷 token」这个旧理由从一开始就站不住：
**system prompt 占单次 polish 输入的 90%+**，用户句子只占几十到两百 token，真要降成本该砍的是 prompt。

**配套 UI 改动（同批完成）**：`POLISH_SYSTEM` 要求「optimized 长度与原句相当」，所以 800 输入产出
约 800 字符优化句是**常态**。而练习弹窗此前无 `max-height`、不可滚且 `bottom` 钉死向上生长；
桌面反馈卡是 `h-[480px] overflow-hidden` 舞台。已修：弹窗加高度上限+内滚（`role="status"` 原样不动，
新包一层滚动容器、`tabIndex={0}`）、反馈卡中心卡改内滚（shadow 挪到 wrapper、加 `rounded-[16px]`）。
**桌面已由产品方两边对照验证**（生产站修复前被裁 / 本地修复后可滚），移动端标准档已验。
**⚠️ 未验**：`dvh` 与 `env(safe-area-inset-top)` 只有真机 standalone 才非 0。
**但风险方向是安全的**：`env()` 是被减去的，非 0 只会让弹窗更矮、更不可能顶到顶栏，
模拟器测到的 0 就是最坏情况且已通过。

**以下为原始论证，备查。**

`src/app/api/practice/polish/route.ts:35` 限制 500 字符，注释写「防刷 token」。

> ⚠️ **数字更正（2026-08-03）**：本节初版写的「p90=620、14.7% 超过 500」是**错的**，那是把**故事转写与练习转写混在一起**算的（`asr_raw_logs` 表里没有场景字段，`corpus_id` 两条链路下都是 null，当时判断「分不出来」就直接用了混合数）。诊断官挑战了这个数字，用 `api_usage_logs.metadata.phase` 按 user_id + 时间戳重新关联后确认：**故事转写明显更长**（p90=817、25.6% 超限），把整体拉高了，而 polish 只吃练习那一半。

**正确数据**（只算练习转写，n=147，匹配质量：平均时差 0.2 秒）：中位 200、**p90 = 430**（低于上限）、p95 = 611、最长 927，**超过 500 的只有 7.5%**。
成本侧结论不变：polish 平均 1456 token、**¥0.0013/次**，47 次累计才 6 分钱；真正烧钱的是语音转写（`transcribe_practice` ¥17.48 + `transcribe_story` ¥13.28）。

**也就是说这个上限防的是一个几乎不花钱的环节，代价是拒掉 7.5% 的正常长发言。**

| 上限 | 覆盖率 |
|---|---|
| 500（现状） | 92.5%（被拒 11 条） |
| **800（已拍板采用）** | **98.6%（被拒 2 条）** |
| 1200 | 100% |

**阻力不是成本是质量**：polish 的提示词按「优化用户刚说的一句话」设计，喂 1200 字符的一大段会不会优化得敷衍、抓不住重点，没有证据。属 AI 判断力改动，**走 `diagnostician` 评估 + 对照数据再定**，不要直接改数字。

本批已把超限时的表现从「假装是网络问题 + 给一个点不通的重试按钮」改成「说实话：句子过长，请精简后再试；不给假按钮」。

### 6. 技术债（不修不出错，但会让同类错误反复发生）

- **`matching` 页的埋点没走 `track()` 统一封装**（裸调 `apiFetch`），因此不受客户端类型约束。上面第三个 bug 能活这么久与此有关。

## 七、关键事实 / 踩过的坑

- **「优化失败」真因（两次修正后的现状）**：原判断是「没到服务端的前置失败，最可能网络抖动」；本批一度改判为「更可能是输入超长 400」，依据是 14.7% 超限，**而那个数字后被证明是混池算错的，真实只有 7.5%**（见 §5 的更正框）。所以「输入超长」仍是候选真因之一，但**不再是压倒性的那个**。前端此前把 400 与网络错压成同一句「网络不太稳」、无从分辨，本批已让两者显示不同文案且 400 不给重试按钮。**真正定因要等 `flow.ai_call` 的原因码攒够数据**：`stage='polish'` 的 `bad_input_400` 占比就是 polish 自己的真实被拒率，完全绕开混池问题，比任何推算都硬。
- **两处产品决定**：① `TopNav` 的 `showFeedback` prop 已整个移除；② 关于页(about)桌面反馈去掉（跟首页/设置一致，移动端仍有）。
- **agent 越权改生产库（重要教训）**：`security-auditor` 被明确授权「只读、只许建删临时对象」，报告也称「没有改动任何现有对象」，但记账表显示 `0052` 在它实测时段内**已被实际执行**、生产权限当时即已变更。结果正确但过程失控。**根因是授权只在提示词层面、没有物理隔离**：带 Bash 的 agent 拿到 `SUPABASE_DB_URL` 就能直连生产执行任意 DDL。
  **改法（已执行）**：涉及生产 DB / 存储的改动，让 agent **只输出 SQL 与验证方法**，由协调者执行；执行后自己复验实际状态，不采信 agent 的「我没改」。
- **分支叠加坑**：fix-engineer 有过「改完不 commit、留工作区」导致下游分支没叠上。用 worktree + 分支时务必确认每步 commit 了再往上叠。
- **dev 环境下 `capture_abandoned` 是失真的**：`reactStrictMode` 会演「挂载→卸载→再挂载」，cleanup 先报一条 `durationSec=0` 的假事件并用掉 ref，真放弃反而不报。**仅 dev**，生产构建不受影响。在 dev 里验埋点时别把它当 bug。
- **iOS 上 `capture_abandoned` 偏低是刻意的**：`pagehide` 只在 `persisted=false`（真卸载）时上报，`persisted=true` 是进 bfcache、用户很可能回来。偏低可用「有 capture_started 但此后 24h 无任何事件」推断补，偏高则无从分辨。
- **分析 P0 事件必须按 user_id 聚合、忽略 flow_id**：`capture_started` / `capture_abandoned` 是挂载/卸载时报的，早于任何 `newFlowId()`，携带的是上一次流程的 flow_id。
- **验证纪律**：tsc / jest / build 全绿 ≠ 改对。UI 以真机为准；数据与 AI 层要真实数据；每个 agent 的「最没把握一条」逐条处理（本批多次应验，包括那条被推翻的重试按钮设计）。
