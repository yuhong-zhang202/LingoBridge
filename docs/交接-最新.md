### P3 补丁 · 漏斗接上埋点起算日（生产真实数据暴露）
P3 上线后第一次拉真实数据就发现七步漏斗**两处倒挂**：
第 2 步 29 人 < 第 3 步 95 人（转化率 327.6%、「流失 -66 人」）、第 5→6 步 105%。

**根因不是 SQL 写错，是拿两个起算日不同的数据源做了减法**：
  · 第 1/3/6 步读表（`consent_records`/`corpus`/`practice_sessions`）—— 内测第一天就有数据
  · 第 2/4/5/7 步读 `flow_events` —— **2026-08-02 才上线**（实测最早一条 `flow.capture_started`
    是 `2026-08-02 19:52:30Z`，全历史仅 346 条/55 人，而同期 corpus 建成 96 人）
  拉 30 天窗口时前 18 天埋点根本不存在 ⇒ 表侧吃满 31 天、埋点侧只有 13 天 ⇒ 必然倒挂。

修法：新增 `flowBaselineInfo()`，接口返 `flowBaseline{baselineStart,crossesBaseline,effectiveDays,
windowTotalDays}`，由 UI 如实标注。**刻意不修数、不编补偿系数** —— 历史埋点无法回填
（`0053` 顶注：谁在什么时候自测过，事后无据可判）。起算日**复用既有的 `FLOW_BASELINE_START`**
（早已存在，其注释原文就写着「窗口跨过这一天时 UI 必须标出」）——**P3 当初没接上这条既有口径，是补的洞**。

## 五、沉淀的教训（都已应验，写进 `CLAUDE.md` 验证纪律）

### 批次二新增（2026-08-14）
6. **改造前先立守卫，且守卫必须做变异测试。** P1 的「零行为变更」不是靠小心，是靠重构**前**
   钉下的两道金标。而金标本身也要证明抓得住 —— 三次变异（percentile 95→94、改一处文案、
   改一条注释关键词）全部转红才算数。**不能失败的守卫等于没有。**
7. **验收方法本身可能是假闸。** 原验收「前后各拉一次线上数字比对」看着严格，实则必然通过：
   区间末端永远是「此刻」，两次抓取间数据本身在变。**设计验收时先问「这个检查在什么情况下会红」。**
8. **上 UI 之前先拉一次真实数据。** P3 上线后第一次拉真实漏斗就发现跨源倒挂（30 天窗口里
   埋点只覆盖 13 天）。**改数据层比改 UI 便宜十倍**，这一步省掉了整轮返工。
9. **计数只能用来定位，结论必须读原文。** 本批次我方五次靠 `grep -c` 下结论然后误报
   （`.DS_Store` 没算进文件数、`revoke` 签名解析把默认值当类型、`security definer` 数到注释里的、
   `text-error` 数到注释里的、shell 的 `|| echo 0` 让计数变成 `"0\n0"`）。**每次都是读了原文才没错报。**
10. **同一个改动的注释要一次改全。** 额度墙窗口 7→30 时改了 SQL 四处、route 两处、测试一处，
    唯独漏了 `fetchQuotaWall` 的函数注释 —— 由 `@fix-engineer` 在下一阶段发现并按红线只报不改。
    **「注释说 30、代码算 7」比两者都错更难查。**

### 批次一（2026-08-12 ～ 08-13）

1. **验证提交内容要读 HEAD 树，不能读索引。** `61bc553` 声称撤销了误跟踪文件，实际只改了 `.gitignore` —— 因为 `git commit -- <路径>` 从**工作区**取内容提交、绕过了 `git rm --cached` 的暂存状态。当时用 `git ls-files`（索引）验证，看到的是假象；`git ls-tree HEAD` 才是真相。
2. **搜索否定性结论要换维度复核。** 曾断言「`supabase_data` 不存在」，实际目录名是 `临时supbase_data`（`supbase` 少个 `a`），按正确拼写 grep 必然扑空。改用**按文件类型扫**才把面扫全。
3. **agent 审代码前先确认分支。** 详见 memory `feedback-agent-branch-context`：红队在落后 317 个提交的工作区里 grep，报「全仓零命中」，据此否掉了一个**完全正确**的修复方案。

5. **数字先核实再报。** 本批次两次报错数：匿名号成本上界（¥3.3 → 实际 ¥45）、匹配往返次数（「串行 118 次」→ 实为 `Promise.all` 并行）。
