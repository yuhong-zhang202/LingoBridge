# 议题台账（DISCUSSION_LOG）

## 这个台账是什么

本文件是 LingoBridge eval loop 的**争议与决策总账**。每一轮 loop 里,任何角色(金标标注、指标、AI 评审、产品、工程)发现的**说不清的地方**都往这里记一条,而不是各自在自己的报告里自说自话。

它记的是**分歧和待定**,不是任务清单。一条进来的标准是:有人认为这里可能有问题,且这个问题不是靠一个人埋头改代码就能消掉的。

## 状态字段谁能改(硬性)

| 状态 | 含义 | 谁能写 |
|---|---|---|
| 待议 | 已入账,未拍板 | 任何角色转条目时,由记录员写入 |
| 已决策 | 人已拍板方向,可能尚未落地 | **只有人**拍板后,记录员据实登记 |
| 已解决 | 讨论结束、落地完成、正式结案 | **只有人**。记录员、AI 角色一律不得自行改写 |
| 已作废（依据来自污染数据） | 条目的**实测依据**读自已被判定污染的导出,不足以支撑原结论 | **只有人**。产品方 2026-07-16 启用此状态。**作废的是依据,不是说结论已被证伪**——需管道修好并重跑全量基线后重估 |

记录员不对条目发表判断、不提解法、不结案。AI 角色报"我修好了"**不等于**已解决——代码修完只是事实,结不结案是人的决定。

## 怎么用

1. 发现争议 → 转给记录员 → 追加一行,状态默认「待议」。
2. 同一问题多角色报告 → 合并为一条,来源列写全,不重复开号。
3. 每轮 loop 结束 → 记录员出「本轮待讨论摘要」:新增几条、按类型分组、优先级排序(只排序,不下结论)。
4. 人拍板 → 记录员把状态改「已决策」或「已解决」,并在条目里留下拍板日期与拍板人。

类型七选一:**合并记录** / 金标争议 / 指标争议 / 产品取舍 / AI稳定不同意金标 / 跨环节风险 / 其他。

## 规则变更(2026-07-16):每次合并 = 台账一条

**「合并记录」类型自 2026-07-16 起启用,由产品方定规则。** 此前台账只记"报上来的争议",不记"做了的事"——结果 `rawCall` / `checkAlignment` / `validate` 这些改动全部没进台账,因为在执行者眼里它们是"实现细节"。**但 validate 决定用户会不会看到模型捏造的维度。**

> **争议只是子集。台账要能重建"这周发生了什么",而不是"这周吵了什么"。**

每一次合并都要记一条,最少三行:(1) 改了什么(**文件:行号级别**,不是"优化了重排");(2) 为什么(解决什么问题 / 依据哪次拍板);(3) 影响哪些用户可见行为(**没有就写"无",但必须显式写**)。

合并记录的状态说明:代码已合并只是**事实**,不等于结案。故一律记「待议(代码已合并,待人确认结案)」,沿用条目 009 的先例——AI 角色报"我修好了"不等于已解决。
