## 3.2 🔴 重排噪声地板（R=3 实测，2026-07-16）—— 今天最重要的产出

**同代码、同输入、`temperature: 0`，三轮跑出三个不同的分。**

```
闸门（官方口径）      轮1     轮2     轮3    极差
──────────────────────────────────────────────
首屏精确率           39.1%   39.1%   36.0%   3.1pp
虚高率               17.4%   21.7%   20.0%   4.3pp
可见区档位命中率      41.8%   40.8%   37.0%   4.8pp
NDCG@5              0.964   0.942   0.943   0.022
Kendall τ           0.768   0.723   0.713   0.056
AI高分母               23      23      25       2

三轮档位全一致率 stability = 81.8% (121/148)
对照：萃取噪声地板 = ±1.0pp（同代码三次 94.61/94.95/95.62）
```

### 结论一：重排噪声是萃取的 3–5 倍，而红线容差按萃取标定

`BASELINE.json` 的 `noise_margin_pct = 1.5` **是按萃取标的，七条红线一直共用它**。
> **用 1.5pp 的容差去守一个极差 4.3pp 的指标，等于每次跑都在掷骰子。**
> **今天所有关于虚高率的争论（27.3 → 11.8 → 17.4）全部在噪声里。** 我们曾为"虚高率降了 9.9 个点"高兴过——那可能有一半是抖动。

### 结论二：`temperature: 0` 不代表确定性

这是今天最反直觉的一条。别再假设"温度 0 所以可复现"。

### 结论三（重要）：稳的和不稳的，分界线正好是「分母由谁控制」

```
✅ 三轮完全一致（极差 0）        ❌ 抖（极差 3~5pp）
─────────────────────────      ─────────────────────
首屏可用率   12.5/12.5/12.5      首屏精确率    分母=AI高条数(23/23/25)
召回精度     30.4/30.4/30.4      虚高率        分母=AI高条数
首屏精确率分子  9 / 9 / 9         可见区档位命中率  分母=AI∈{高中低}
noMatch      0 / 0 / 0
```
**稳的那几条，分母都由金标定死**（故事总数 40 / 金标标注对 148 / 金标高总数 11）。
**抖的那几条，分母都是 AI 自己控制的。**

> **LOOP.md 红线设计原则第 2 条（"分母必须用金标定死的量"）在这里被独立验证了。** 它当初是从"分母缩水能刷分"推出来的，**没想到它同时还决定了指标稳不稳**。同一条原则，两个独立的理由。

## 5. 红线设计三原则（已写进 LOOP.md，这里给实证）

**1. 精确率天然可用"少预测"刷分，必须配召回率。**
实测：一次改动让首屏精确率 40.9% → 52.9%，看着涨 12 点。逐条核对是 **9/22 → 9/17**——**命中的就是同样那 9 条，连集合都一模一样**，掉出分母的 6 条没有一条是金标高。把分母摁回 22 = 40.9%，**零改善**。
对策：召回率分母 = 金标高总数（11），**由金标定死，AI 控制不了**。踢候选出高档 → 精确率涨、召回率不动 → 一眼看穿。

**2. 分母必须用金标定死的量，不能用 AI 能控制的量。**
实测：首屏可用率分母误用 `len(d['stories'])`（导出全部故事）。`run-ranking.ts` 一改，导出从 40 变 100，而金标只覆盖 40 → **12.5% 被算成 5.0%，报了个假 FAIL**。
按金标对齐的口径天然抗漂移（召回精度按 gold∩recalled 算，分母漂移时纹丝不动），按产物规模算的不抗。

**3. 一条红线只防一个方向，成对的红线才防得住取舍。**
只守"精确率↑ + 虚高率↓"，最省事的刷分法是把所有候选压到阈值以下：两条都变好，用户看到空屏。所以要有"首屏可用率不许跌"对冲。**实测拦住过一次真实的收紧刷分。**
> 设计新红线时先问：想刷这条线最省事的做法是什么？那个做法会伤到什么？把那个"什么"也变成红线。

## 8. 踩过的坑（新窗口最容易重犯）

**① 聚合数字会骗人 —— 总分回到基线 ≠ 修好了**
案例：S036 首修后萃取总分从 93.6% "恢复"到 94.9%，真相是 **S041 恰好恢复(-1错) + S100 新冒一个错(+1错) + S036 本身原地不动** 的巧合。
**铁律：逐条核对目标条目本身，不许用总分结案。** 已写进 `.claude/agents/red-team.md`。

**② 精确率能靠缩分母刷** —— 见第 4 节。**9/22 → 9/17，分子一个没动。**

**③ 枚举措辞的规则治不住模型 —— 它会发明新说法绕过**
案例：规则列了词表（「需微调」「不是…」「未体现…」），S067 发明「**非严格符合**」照给 88 分，规则完全落空。
**规则要给判据（能不能反复见到 / 主语是谁），不要给词表。**

**④ 拍脑袋估算高了 2-3 倍，差点去修一个不存在的病**
案例：估算 35 道候选输出 ≈4130 token「顶穿 4096」→ 实测只有 ~1800。
**更糟的是：如果照那个假设改了 maxTokens，真凶（30 秒超时）会继续存在，而我们会以为修好了。**

**⑤ 分批 / 单独问 = 换尺子**
重排的本质是**横向比较**——模型要在 35 道里判断哪道最贴合。分批后每批只看 8 道，**第 1 批的"最好"和第 4 批的"最好"用的不是同一把尺**，引入**我们没有指标能测到的偏差**。
同理否掉「补缺循环只单独问缺的那几道」。**替代：整批重问，最多 3 轮，尺子不变。**

**⑥ 改 prompt 有全局副作用，不是精准打击**
案例：只想治 4 条，实际 13 条里 5 条漂移且方向不受控（S051/S084 反而**涨**了，S084 金标=低 = 新增虚高）。全部 293 条候选：旧分 <40 段平均 **+5.1**、60-84 段 **-9.8**、≥85 段 **-8.1** —— **整张校准表在动**。
**改 prompt 必须预注册预期 + 逐条核对目标与非目标条目。**

**⑦ 三次都在 prompt 上找原因，第四次才想到查管道**
管道审计官原话。**下 "AI 判断力有问题" 的结论之前，先跑 `@pipeline-auditor`。** LOOP.md 已把它卡在"跑基线"和"@diagnostician"之间。

**⑧ `temperature: 0` 不代表确定性**
同代码、同输入、温度 0，三轮跑出三个不同的分（虚高率 17.4/21.7/20.0）。**别再假设"温度 0 所以可复现"。**

**⑨ 别把历史记录改成"正确"的数字**
要求"全仓库不再有 48/43 个观察点"是个偷懒的验收标准——`观察点审计.md`、`项目总览`、`交接文档06-04` 里的 43/44 **当时就是对的**。fix-engineer 拒绝改它们，理由是「**改历史记录会抹掉演进过程**」。它对了。**笔误订正和改写史料是两回事。**

**⑩ `| tee` 会吞掉退出码**
`bash regression-all.sh | tee log` 返回的是 tee 的退出码，FAIL 被伪装成 exit 0。用 `; exit ${PIPESTATUS[0]}`。

## 9. 停机规则（LOOP.md 有全文，这里给要点）

**只有四条必须停下问人：**
1. 用户能看到的东西变了（文案/画面/交互）
2. 要改金标 / 标准 / 指标定义 / 红线数值 / **产品不变式**
3. 红线之间**真**冲突（改动让某条红线 FAIL 且**无法两全**）
4. **动了零红线环节的 prompt**（`analysis.ts` / `practice.ts` / `restructure.ts`）——自动挂旗，不许静默合并

> 第 4 条是**哑铃**，不是解法。真正的解法是给这三个环节建 eval（大工程，未做）。在那之前用"改动必挂旗"换一点安全，代价是慢。
> **看不见的地方不许自己走。**

**分界线（拿不准时用这条判）：**
> **「我们不知道 X，却声称 X」= bug，自主修。**
> **「我们知道 X，但要不要告诉用户 / 怎么告诉」= 决策，问人。**

**特别澄清**：`@pipeline-auditor` 判"管道有问题"后，**停机的目的是让结论作废，不是让每个修法都问人**——修管道本身照常自主推进。

**为什么规则这么窄**：2026-07-16 一轮 loop 停了 7 次问人，**只有 1 次是真产品决策**。规则宽 = 看起来谨慎，实则失职——每次不必要的停机都在把判断责任推回给人，而人雇这套 loop 就是为了不用做这些判断。

## 13. 一句忠告

今天最贵的教训不是任何一个 bug，是这个：

> **我们花了两轮 prompt 修复、一次分诊、一份 13 条清单去调整 AI 的判断力，而真相是喂给它的数据本身就是错配的。**
> 三次都在 prompt 上找原因，第四次才想到查管道。

**接手时，先怀疑管道，再怀疑模型。**

晚上又学到第二条，它和第一条是同一个形状：

> **管道修好之后，我们量出了噪声地板 ±3~5pp —— 而我们一整天都在用 1.5pp 的容差争论 4pp 的差异。**
> 先怀疑管道，再怀疑模型；**但在这两者之前，先问一句"这个数字本身可信吗"。**

**顺序是：尺子 → 数据 → 模型。** 今天我们从最后一环开始，倒着走了一整天。
