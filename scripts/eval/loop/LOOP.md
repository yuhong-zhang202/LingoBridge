# Loop Engineering 跑法说明(大白话版)

> 一句话:你雇了 7 个 AI 员工互相盯着干活,你只在两个关口拍板,其他时间它们自己转。

## 这套东西是什么

- **9 个 AI 员工**(`.claude/agents/` 下):指标设计官、**管道审计官**、诊断官、修复工程师、红队、产品经理、记录员、**红线设计官**、**基线实施官**。每人一份"岗位说明书",写死了它能干什么、不能干什么。

  > **后两个是 2026-07-17 产品方指出空档后新增的。** 原本 7 个角色里**没有一个负责设计红线、也没有一个能实施红线**——
  > `@metric-designer` 管「怎么量」不管「多少算不合格」,`@fix-engineer` 物理碰不到考卷,其余只读。
  > 于是「红线定多少、容差多少、哪条该废」和「谁去改 BASELINE.json」两件事**默认落到主会话**,
  > 而主会话没有岗位约束,**且同时是提案方、实施方、和裁定红队意见的人——三顶帽子一个头**。
  > 产品方原话:「@metric-designer 应该提案啊,为什么提案也是你,加两个角色吧,一个负责实施,一个负责红线设计官,你负责总览全局」。
  >
  > | 角色 | 帽子 | 能碰 |
  > |---|---|---|
  > | `@redline-designer` | **提案** | **没有 Write/Edit——物理只提案** |
  > | 主会话 | **总览 + 交人拍板** | — |
  > | `@baseline-engineer` | **实施** | 红线/算分脚本/回归守卫;**金标与不变式物理碰不到**(`guard-golden.sh human-only` 档) |
  > | `@red-team` | **证伪** | 只读 |
  >
  > **2026-07-17 补充：提案≠实施 适用于【产品功能】，不只红线/评测。** 派任何构建类任务前，分别点名 proposer 和 implementer，**同一个 agent 就停**——**`@fix-engineer` 不许给自己要实施的方案出稿**。
  > 产品功能域目前缺专职 designer：技术设计临时用通用 **`Plan` 架构官**（只读、无 Write/Edit）出方案 → `@fix-engineer` 实施 → `@pm-reviewer` 审用户可见影响 → verify 验证。产品功能若反复出现，照 `@redline-designer`↔`@baseline-engineer` 立 feature-designer↔fix-engineer 一对。
  > 起因：当日"冻结匹配结果"任务上主会话让 fix-engineer 既设计又实施，被产品方当场纠正（"实现者不该给自己出方案"）；根因是套用了同样瑕疵的先例、没从原则重推。**优先级/顺序由主会话定并驱动，不外推给产品方；只升级真正属产品方权限的决策。**
- **3 个脚本**(`scripts/eval/loop/` 下):两个"门禁"(guard-golden 拦住修复工程师碰考卷;only-ledger 让记录员只能写台账)+ 一个"回归守卫"(跑完全部评估、和红线比数字,退步就报 FAIL——这个用脚本不用 AI,因为比数字这种事,脚本绝不含糊,AI 会"觉得差不多")。
- **1 本台账**(`DISCUSSION_LOG.md`,记录员管):所有 AI 拿不准、有争议、"AI 稳定不同意金标"的事,全记这里。loop 跑完你我一起过一遍,决定哪些要推翻重议——这就是你要的记录员机制。
- **1 个红线文件**(`BASELINE.json`):回归的及格线。改它=改考卷,只有你能改。

## 安装(一次性,5 分钟)

1. 把整个包解压到仓库根目录(目录结构已对齐:`.claude/agents/` 和 `scripts/eval/loop/`)。
2. `chmod +x scripts/eval/loop/*.sh`
3. **重启 Claude Code 会话**(直接放文件进磁盘的 agent,要重启才认;以后用 `/agents` 界面改则立即生效)。
4. 提交到 git,团队共用。

## 为什么它不会自己骗自己(核心设计)

- **改代码的人碰不到考卷**:修复工程师想写 golden/评估脚本,hook 拒绝——不是靠它自觉。
  > ⚠️ **2026-07-17 实测订正(台账 066)**:这句话此前写的是「**hook 直接物理拒绝**」,**那是不成立的**。
  > `@fix-engineer` 亲跑实测:`Write`/`Edit` 写保护路径 → **被拦 ✅**;但 **Bash 完全不在拦截面内** ——
  > `printf ... > scripts/eval/loop/specs/x.md` **文件真的建出来了**,`touch BASELINE.json` 也一路放行。
  > 而 fix-engineer **有 Bash 工具**,即它一直可以用 `cat > golden/ranking.v1.json` 改金标,一行拦不住。
  > **已修**:guard-golden.sh 加了 Bash 面拦截。但**它是字符串启发式,不是 shell 解析,做不到完备**
  > (变量拼路径、base64、python -c 拼字符串都能绕)。**它挡「顺手写」,挡不住「存心写」。**
  > 真正的保证只有两条:**(1) 不给需要写考卷的 agent 配 Bash;(2) 人审 diff。**
  > `@recorder` 之所以真的安全,不是因为 hook,**是因为它的 tools 里根本没有 Bash**。
  >
  > **教训(比这个洞本身更值钱)**:这套 loop 最核心的一句设计宣言,**从来没有人试过它是不是真的**。
  > 红队从脚本内容**推断**它拦不住 Bash;主会话 grep 了 settings.json 没找到 hooks 就**推断**它根本没注册(**也错了**——hooks 挂在 agent frontmatter 里,确实会触发)。
  > **两边都在推,没人试。跑一次就知道了。**
- **有人专职唱反调**:红队的唯一 KPI 是"证明改善是假的"。它查考卷动没动、备选变宽没有、改善幅度是不是噪声、有没有按下葫芦浮起瓢。
  > (「<1.5 个百分点不算数」已作废——那是**萃取**的噪声地板;重排实测极差达 11.3pp。容差改逐条标定,见 BASELINE.json)

### 红队结论被驳回,走什么程序(2026-07-17 产品方交主会话判断,已成文)

**红队的结论,主会话不得单方面驳回。驳回必须同时满足三条,缺一即视为接受红队结论:**

1. **驳回理由必须是可复现的实测,不是论证。**
   先例(成立):驳回「红线2 是可证明的死线」——穷举出 hit=11 时丢光 S040 会让红线1 PASS 而红线2 单独 FAIL,**那是能跑的**。
   反例(不成立):「我觉得它有产品语义」「保留系语义锚点而非检测力」——那是态度,不是证据。
2. **驳回必须再过一次红队**(带上驳回依据重审),**或由人亲自看**。
3. **驳回入台账,标明「红队结论被驳回」,与被驳回的原文并列存档。**

**为什么**:红队是唯一制衡主会话的角色。**主会话对唯一的检查者行使否决权而无人复核,等于没有检查者。**
> 实证(2026-07-17):主会话自提 BASELINE v3,红队抓出四个错——把构造常数当实测、写了一个事实错误、n=3 三次援引全部倒向更松、用一个看不见该模式的统计量宣布漂移不存在。**四个里没有一个是主会话自查出来的。**
> 同一轮里,主会话驳回了红队的第 5 条,**且是自己拍的**——程序上不合格,已记台账 063「红队结论被驳回的首例」。
- **数字关卡是脚本**:回归守卫是 shell 脚本,FAIL 就是 FAIL,没有"我觉得问题不大"。
- **拿不准的不许自己判**:AI 稳定不同意金标的条目(以前 S018/S044 这种,最后证明是我们标错了),任何角色都无权判死,只能进台账等你裁决。

## 一轮循环怎么跑(以重排环节为例)

**第 0 步·定标准(每个环节只做一次)**
在 Claude Code 里说:
```
@metric-designer 为重排环节(ranking.ts)设计评估指标体系和金标规范,产出提案。
```
它给你一份提案。**【人闸 A】你看提案,批准或改**。批准后让主会话把 spec 存到 `scripts/eval/loop/specs/`(存进去就被 hook 保护,谁也改不了)。

**第 0.5 步·造考卷(诚实说:这步省不掉人)**
按 spec 建金标/标注。像萃取那次一样:AI 预填、你确认。这是全 loop 唯一需要你花力气的地方,但只花一次。

**第 1~7 步·自动循环(一句话启动)**
```
按 scripts/eval/loop/LOOP流程 执行一轮:跑评估基线 → @pipeline-auditor 先查输入 →
(管道干净才继续) @diagnostician 诊断出提案 →
我批准的提案交 @fix-engineer 实施 → bash scripts/eval/loop/regression-all.sh 全链路回归 →
@red-team 审计真假 → @pm-reviewer 查用户可见影响 → 各方挂旗统一交 @recorder 入台账 →
最后给我:回归结论 + 红队结论 + PM结论 + 台账新增摘要。
```
主会话会依次派活。中间除了"批准诊断提案"那一下,你不用管。

**为什么 @pipeline-auditor 必须卡在"跑基线"和"@diagnostician"之间:**
诊断官的岗位设定是"归因 AI 的判断",它天然会把一切异常解释成判断力问题——包括那些其实是"喂进去的东西就是错的"。管道审计官只查一件事:**输入对不对**(题目映射、候选来源、字段有没有串、prompt 拿到的上下文是不是它该拿的)。
先例:曾把一个管道 bug 当成 AI 判断力度量,基于错数据调了 prompt。**管道判"有问题"→ 停下问人,不许进诊断**——因为基于错输入做的一切归因和修复都是白费,而且会污染台账。

**第 8 步·【人闸 B】你只看三样东西**(每轮几分钟)
1. 回归守卫:PASS 还是 FAIL
2. 红队结论:✅真改善 / 🟡可疑 / ❌刷分
3. 台账新增的旗
都干净 → 说"合并";有旗 → 拉个会话把那面旗聊清楚再定。

**循环直到**:指标达标,或台账里的旗需要你先拍板。

## 自主运行规则(agent 自己能干到哪、哪里必须停)

这条规则的分界线不是"难不难",是**"错了谁来兜"**。数字和代码错了,回归和红队兜得住;产品判断错了,只有用户兜——所以那类事一律停。

### 【必须停下问人】只有四条,少一条都不停

1. **用户能看到的东西变了**——文案、画面、交互。
2. **要改金标 / 标准 / 指标定义 / 红线数值 / 产品不变式**。包括 `golden/*.json`、`BASELINE.json` 的数字、闸门口径的分子分母、新增或删除一条红线、`docs/PRODUCT_INVARIANTS.md` 的任何一条。**"这条金标标错了"也不许自己改,只能进台账等裁决。**
3. **红线之间真冲突**——改动让某条红线 FAIL 且**无法两全**。注意:能两全就不是冲突,是还没想够,继续想。
4. **动了零红线环节的 prompt**——`src/services/analysis.ts` / `practice.ts` / `restructure.ts`。**自动挂旗上报,不许静默合并。**

### 关于第 4 条(哑铃红线)

`analysis` / `practice` / `restructure` **目前没有任何 eval 和红线**。回归守卫跑完全绿,**不代表它们没坏——代表我们测不到**。
其中 **`analysis` 是用户点进题目后看到的全部内容**。改它的 prompt 而红线全绿,是这套 loop 目前最大的盲区。

这条是**哑铃**,不是解法:真正的解法是给这三个环节建 eval(大工程,未做)。在那之前,用"改动必挂旗"换一点安全,代价是慢。
> **看不见的地方不许自己走。**

### 【自主做,不用问】

- **修 bug——包括产品行为的 bug**。前提:修完所有红线仍 PASS。
- **@pipeline-auditor 判"管道有问题"后的修复动作**。停机的目的是**让结论作废**,不是让每个修法都问人。判定一出,当前所有基于该数据的结论立即失效并入台账;修管道本身照常自主推进。
- **内部实现选择**:join key、排序键、校验方式、重试策略、日志留存方式——用户看不见的,都是你的。
- 诊断归因、跑回归、重跑、派红队、派 PM、记账。
- **自动合并**:仅当**三个条件同时成立**——回归 PASS + 红队 ✅真改善 + PM 无旗。三缺一即停。

### 金标复审队列(2026-07-16 新增)

> **AI 稳定分歧(R≥3 全一致)+ 理由引用 rubric 原文且自洽 → 自动进金标复审队列。**
> **不许自己改、不许绕过。**

两个条件缺一不进队列:
- **R≥3 全轮一致**——重排噪声地板实测 ±3~5pp,单轮分歧是噪声不是信号;
- **理由引用 rubric 原文**,指出金标违反了**金标自己的明文定义**(先例 S074:rubric 写「高=原样能答」,而"潜水五年"答不了"describe a time you saw")。**这是指出不自洽,不是提意见。**

进了队列 = 挂在台账等人裁决,**不是"可以改了"**。改金标永远是必停第 2 条。

**为什么要这条规则**:2026-07-16 之前,没有任何角色的职责包含"金标本身对不对"。`@pipeline-auditor` 查喂给模型的输入,`@diagnostician` 做 AI 错例归因——**尺子没人管**。结果:管道错位有人负责找,而**金标存疑(S074)和金标不自洽(台账 004)全是撞出来的**。
本文档的忠告写着「尺子 → 数据 → 模型」,规则却漏了第一环。现在补上:`@pipeline-auditor` 查金标的**结构与设计**(不自洽、抽样权重),`@diagnostician` 出**待复审清单**(稳定分歧 + rubric 冲突)。**两者都只出清单,判定全归人。**

> **AI 有把握的时候,恰好是 AI 与金标强烈分歧的时候,也恰好是循环性最致命的时候。**
> 用模型的意见去覆盖金标,再拿改过的金标去测这个模型,测出来的是它跟自己的一致率。

### 分界线(拿不准时用这条判)

> **「我们不知道 X,却声称 X」= bug,自主修。**
> **「我们知道 X,但要不要告诉用户 / 怎么告诉」= 决策,问人。**

例:重排降级时把未打分的题落库成 `match_level='high'`——我们不知道它贴不贴合,却声称"高匹配",**属前者,自主修**。
而"降级时该给用户看什么画面"——我们知道自己不知道,问题是怎么呈现,**属后者,问人**。

### 为什么规则要这么窄(2026-07-16 的教训)

那天一轮 loop 停了 7 次问人,**只有 1 次是真正的产品决策**,其余 6 次是把"修 bug"和"内部实现选择"误当成了决策。代价不只是慢:**每次不必要的停机都在把判断责任推回给人,而人雇这套 loop 就是为了不用做这些判断。**
规则宽 = 看起来谨慎,实则失职。停机要贵、要少、要真。

### 【记录员】每次合并 = 台账一条

**不是"有争议才记"。每一次合并都记一条**,最少三行:改了什么(文件:行号级别)/ 为什么 / 影响哪些用户可见行为(无就写"无",但必须显式写)。

**为什么(2026-07-16 的洞)**:此前只记"报上来的争议"、不记"做了的事"。结果 `rawCall`/`checkAlignment`/`validate` 的改动全没进台账——在执行者眼里它们是实现细节,**但 validate 决定用户会不会看到模型捏造的维度**。
> **争议只是子集。台账要能重建"这周发生了什么",而不是"这周吵了什么"。**

此外,所有**争议、决策、停机点**照旧入台账。停下问人的那一刻同时记一条:停在哪、为什么停、等谁裁什么。**决策本身也要记**——不然下一轮没人记得为什么当初这么定,又会重议一遍。

## 三份制品的分工(别搞混)

| 文件 | 性质 | 回答什么 | 谁能改 |
|---|---|---|---|
| `docs/PRODUCT_INVARIANTS.md` | **规范性** | **什么不许变** | 只有人 |
| `docs/匹配链路-权威文档.md` | 描述性 | 现在怎么工作 + 判例 | agent 可更新描述 |
| `DISCUSSION_LOG.md` | 流水账 | 发生过什么、谁拍的板 | 只有 @recorder |

**描述变了改权威文档,承诺变了才改不变式。** 混淆这两者的后果是:把一次实现变更伪装成产品决策,或者反过来——把产品决策藏在实现变更里。

**扫改动用**:`bash scripts/eval/loop/product-surface-diff.sh <since-commit>` —— 从 diff 里只捞产品表面(文案/阈值/展示逻辑/降级路径/prompt/零红线环节),按风险排序。**它是过滤器不是结论**,没捞到不代表安全。

## 红线怎么设计才不会被刷(2026-07-16 实测教训)

**1. 精确率天然可以用"少预测"刷分,必须配召回率。**
精确率 = 判对的 / 判了的。**分母由 AI 自己控制**——它只要少判几个,分母就变小,精确率就涨,分子可以一个没动。
实测:2026-07-16 一次改动让首屏精确率 40.9% → 52.9%,看着涨了 12 个点。逐条核对发现分子是 **9/22 → 9/17**,**命中的就是那同样的 9 条,连集合都一模一样**,掉出分母的 6 条没有一条是金标高。把分母摁回 22,精确率 = 40.9%,**零改善**。
对策:**任何精确率都要配一条召回率**。召回率 = 判对的 / 金标里本来有的,**分母由金标定死**。
- 踢候选出高档 → 精确率涨、召回率不动 → 一眼看穿
- 踢掉一个真的高 → 召回率跌 → 拦住

**2. 分母必须用金标定死的量,不能用 AI 自己能控制的量。**
同日第二次踩:首屏可用率的分母写成"导出里的全部故事"。`run-ranking.ts` 一改,导出从 40 个故事变成 100 个,而金标只覆盖 40 个 → 12.5% 被算成 5.0%,报了个假 FAIL。
**凡是"按 X 数算"的指标,X 必须是金标覆盖的那批,不是产物的规模。** 按金标对齐的口径天然抗这种漂移(同日实测:召回精度按 gold∩recalled 算,分母漂移时纹丝不动),按产物规模算的不抗。

**3. 一条红线只防一个方向,成对的红线才防得住取舍。**
只守"首屏精确率↑ + 虚高率↓",最省事的刷分法是把所有候选压到阈值以下:两条都变好,而用户看到的是空屏。所以要有"首屏可用率不许跌"对冲。
**设计新红线时先问:如果我想刷这条线,最省事的做法是什么?那个做法会伤到什么?把那个"什么"也变成一条红线。**

**4. 参数与现实对不上时,解释差额,禁止用"自适应 / 稳健于偏差"绕过。**
> **声明让位给实测的每一处,都是一个潜伏 bug。**

实证(台账 036/052):抽样声明 `hiddenSampleRate: 0.2`,实际标注 59 条而非理论的 41 条——**差 18 条**。
这个差**当天就被发现了,还被写进了注释**:

> 「用数据实测 S = 隐藏候选总数 / 隐藏已标数,**不写死 ×5,稳健于实际标注量偏差**。」
> 「`hiddenSampleRate?: number  // 隐藏区抽样率(如 0.2);算分优先用数据实测 S,此值仅交叉校验/留档`」

作者知道偏离,选择了"稳健于偏差"——**用实测绕过去,而不是问一句为什么偏**。那个绕法**就是 036 这个 bug 本身**:
它不是疏忽,是一次深思熟虑的妥协,把一个没查清的偏差用"自适应"包装成了特性。
`hiddenSampleRate` 由此从「抽样设计的声明」降格为「仅交叉校验/留档」——**意图让位给了现象**。
真相后来查清了:抽样是 per-story 的 `i % 5 === 0`,每故事必取第 0 条 → 实际抽 `ceil(n_i/5)`,
40 个故事各自向上取整,累积 204 → 59。**一个 `ceil`,困惑了一整天。**

> **失手不在没发现差额,在发现了却选择适应它,而不是解释它。**
> 一个"自适应"的实现若是为了容纳一个未被解释的偏差,那它不是稳健,是把问题固化进了代码。

同一形状在本项目至少四处:`hiddenSampleRate: 0.2`(靠实测绕过)、`ExtractionPick.reason` 的类型谎言、
`topic_only 不走召回`(靠数据约定)、`?? 100`(把"不知道"当容错)。
**它们全是:写下一个声明,然后让代码去适应它不成立的事实。**

### 原则 4 的实操细则:挪阈值前先看分数直方图

**挪任何阈值前先看分数直方图,线放凑整谷底。**
(原则防态度,细则防手法;原则列表保持短而行为性,手法归 checklist。)

实证(2026-07-16,2991 条候选):模型的凑整点是 **10 / 5 / 25 / 15 / 20 / 40 / 35**。
```
55: 70 █████████████████
60: 33 ████████            ← 新可见线,落在谷底
65: 79 ███████████████████
恰为 60 = 33/2991 = 1.10%    对照 旧线 40 恰为 40 = 150/2991 = 5.02%(高 4.6 倍)
```
**40 正是模型的常用凑整点,60 不是。** 线踩在凑整点上时,"题目显示与否"取决于模型凑整到 40 还是 35——
这与台账 042 判低档为"假精度"是同一现象,只是那次在档内、这次在档界。

## 建议的环节顺序(按性价比)

1. **重排**(有现成全量数据、你的高中低三档标准早就定了)
2. **题目分析**(一半是硬规则,机器全自动可查)
3. **故事整理 restructure**(它在最上游,错了全链路遭殃)
4. **教练对话**(最难,要写模拟用户脚本)
5. 转写/发音(要音频样本,可能等内测)
