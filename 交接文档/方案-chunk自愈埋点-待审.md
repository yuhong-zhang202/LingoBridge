# chunk.self_heal 埋点方案 —— 评估结论：【暂不做】（2026-07-21）

> 状态：**已评估、产品方决定暂缓**。后续若海外白屏频繁出现再重启。

## 背景
chunk 加载失败自愈（`5ecd0b0`）目前只 `console.warn`、零可见。想加埋点上报，
把"白屏自愈发生过"变成可查。产品方原拍板走免鉴权端点（决策 B）+ 只收粗粒度（决策二）。

## 为什么暂缓（security-auditor 评估后的判断）
security-auditor 从攻击视角评估免鉴权写库端点 `/api/beacon`，挖出方案作者没想到的两条 🔴：

1. **🔴 可冒充/污染核心看板**：底层 `logEvent` 无条件信任 caller 传入的 `event/user_id`。
   免鉴权端点若透传 body 字段，攻击者能 POST 假 `match.result`、挂到任意用户 uuid，
   **污染驱动决策的匹配成功率看板**（不只是 self_heal 那格）。现有 `/api/events` 靠
   "要 session + 硬编码事件名"挡住，免鉴权丢了这层。必须实现铁律：event/user_id 全写死、
   一字节不读 body。
2. **🔴 限流 map 可被灌爆 OOM**：per-IP 内存计数器本身是张表，伪造海量假 IP → map 无界
   膨胀 → 单实例 OOM → **全站宕**（单实例无冗余）。
3. **🟡 跨站 drive-by 灌水**：sendBeacon 无视 CORS，第三方站可借访客浏览器替攻击者写库、
   用真实 IP 绕限流。
4. **地基未验**：整条限流防线取决于"Zeabur 反代把真实 IP 放哪个 header、能否被伪造 XFF
   覆盖"——**这是没测过的部署事实**，取错则 per-IP 限流零防护。

## 结论：复杂度 > 价值（内测阶段）
为"知道白屏发生没发生"这一个信息，要付：免鉴权端点 + 防冒充硬编码 + 有界限流器 +
DB 每日兜底 + Origin 过滤 + 时序抹平 + 实测 Zeabur IP —— **7 层防护 + 一个没测的地基，
而它本身还抓不全**（网络完全断的那类漏掉）。不该为一个遥测开这么重的免鉴权写库口子。

**产品方 2026-07-21 决定：暂不做。** 现状够用：
- 自愈机制本身已生效（`5ecd0b0`，带防死循环闸）——白屏会自动刷一次恢复。
- 想知道某用户有没有白屏：让 ta 开 Console 看 `console.warn`，或截图发来。

## 重启条件与届时的两条路
若内测/上线后**海外白屏频繁**、需要自动捕捉：
- **方案甲（轻，优先）**：不开端点。自愈时写一条到浏览器 `localStorage`（时间/类型），
  用户在设置页点"发送诊断"按钮时走**现有鉴权** `/api/events` 上报（登录态、零新增攻击面）。
  覆盖"没建 session 的最早期白屏"（存本地不需 session）。代价：非全自动、要用户点一下。
- **方案乙（重，规模大再上）**：按 security 清单全做 7 层防护 + 先实测 Zeabur 真实 IP header。
  能全自动，但工作量/风险大，且仍抓不全。

## 更上游的根治（与埋点无关，海外体验的真解）
海外白屏物理根因＝柏林→香港距离（部署文档 §10）。**自定义域名 + Cloudflare 边缘缓存静态
资源**能让海外根本不容易触发白屏，比"白屏后埋点"治本。产品定位国内，优先级产品方定。
